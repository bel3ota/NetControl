# Security

## Threat model

NetControl is an administrative tool for networks the operator is authorized to
manage. The relevant assets are:

- gateway credentials and API keys;
- session tokens and administrator passwords;
- the device inventory and monitoring history (potentially sensitive);
- the integrity of access-control rules (a false “blocked” is a security failure);
- the host running the service and its database.

Threats considered:

- a network attacker who can reach the management API;
- a malicious local user on a shared host;
- credential leakage through logs, API responses or the database;
- command injection into nftables/tc/SSH/HTTP adapters;
- scanning or enforcing outside the authorized scope;
- a gateway returning a false success;
- stolen/expired mobile sessions;
- privilege escalation through the helper.

Out of scope: defeating Wi-Fi encryption, 802.1X, VLAN isolation, client
isolation imposed by the network operator, or any authentication you do not
control.

## Implemented controls

### Passwords and sessions

- Argon2id password hashing with per-password random salts.
- Minimum 10 characters and three character classes; generated bootstrap
  passwords always satisfy this.
- Opaque 32-byte session tokens; only a SHA-256 digest is persisted.
- 12-hour default expiration; login rate limit of 15 failures per IP per 5
  minutes; success clears the counter.
- Sessions are revoked on password change; disabled users cannot validate.
- Bearer and `X-API-Token` headers supported; SSE accepts `?token=` because the
  browser EventSource API cannot set headers. Tokens are never logged.
- Roles: `admin` for mutations and audit; `viewer` for read endpoints.

### Secrets at rest

- Gateway passwords/API keys are sealed with AES-256-GCM.
- The 32-byte master key is created once at `~/.config/netcontrol/master.key`
  (mode `0600`) and stored separately from the SQLite database.
- The API never serializes secrets; only `has_secret` is exposed.
- Audit/log output passes through a redactor for password/secret/token fields.
- The first-run admin password file is mode `0600` and deleted after the first
  administrator login.

### Transport

- HTTP is loopback-only by default.
- A non-loopback listener without TLS is refused unless
  `NETCONTROL_ALLOW_INSECURE_REMOTE=1` is explicitly set (documented as lab-only).
- `server.allow_remote` must also be enabled.
- TLS is provided by rustls with certificate/key files.
- CORS uses an explicit origin allowlist (Tauri and local dev), credentials
  enabled, no wildcard headers; unknown origins are rejected by the browser.

### Input validation and injection resistance

- IP addresses, CIDRs, MACs, interface names, ports and rates are validated
  before use.
- nftables scripts are generated from validated tokens; tc is invoked with an
  argument vector, never a shell.
- SSH remote scripts quote every value with single-quote escaping, and host/
  username/port are validated. Adapters never accept arbitrary commands from
  clients.
- SQL uses parameters for all user values; sort columns are chosen from a
  hard-coded allowlist.
- HTTP request bodies are limited to 1 MiB; card inputs are length-limited.
- Scan scope: only RFC1918/ULA/link-local by default; public ranges require an
  explicit `allow_public`/`--allow-public` and authorization confirmation.
- Every scan requires `confirm: true` / `--yes`; destructive actions require
  confirmation as well.
- No arbitrary shell execution from the API, UI or MCP surfaces.

### Privilege separation

- Discovery and the service run unprivileged.
- The only privileged component is `netcontrol-helper`, invoked through a
  specific sudoers rule.
- The helper validates every field, supports only six actions, and refuses to
  run without root.
- It does not read arbitrary files, does not execute shells, and does not accept
  command strings.
- The systemd unit uses `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`,
  `RestrictRealtime` and a minimal capability bounding set. `CAP_NET_ADMIN` is
  in the bounding set so the sudo helper child can edit nftables; the daemon
  itself does not hold it as an effective capability.

### Network scope and behavior

- No scanning of public addresses by default.
- No attempt to bypass Wi-Fi security, VLANs, client isolation or router
  restrictions.
- No fake devices, traffic or enforcement results. Unsupported operations are
  explicit.
- Gateway operations read state back; unverified changes are reported as
  failures and never persisted as blocked/limited.

### Android

- Session token and server URL are encrypted with an AES-256-GCM key held in the
  Android Keystore; the IV is generated by the Keystore.
- Cleartext HTTP is permitted only for local setup convenience and warned about
  prominently; HTTPS is recommended for all remote use.
- The app performs no local enforcement and requires no root.
- Certificate validation uses the Android system trust store; self-signed
  certificates require installing a trusted CA.

### Audit

Every login, scan, device edit, trust change, block/unblock/pause, limit change,
gateway change and settings update is written to `audit_logs` with actor,
outcome, target and a redacted detail. The audit view is admin-only.

## Known gaps and hardening recommendations

- The API uses bearer tokens rather than short-lived access + refresh tokens;
  for internet-facing deployments, place it behind a VPN or a reverse proxy with
  MFA and rate limiting.
- There is no built-in multi-factor authentication.
- Audit logs are local and not cryptographically chained; ship them to a SIEM
  for tamper evidence.
- TLS certificate distribution to Android is the administrator's responsibility.
- The helper's sudoers rule is powerful by design; restrict it to the exact
  binary and service account and review it after upgrades.
- Router adapters' security depends on the credentials and transport you
  configure. Prefer dedicated least-privilege accounts and TLS.
- Debug builds (including the supplied APK) are not hardened for public
  distribution; sign release builds with your own key.
- No formal third-party security audit has been performed. Treat the
  non-Linux adapters as requiring validation on your hardware before production.

## Reporting

Do not test against networks you do not own or have written authorization to
manage. Report security issues privately to the maintainers rather than opening
a public issue with exploit details.
